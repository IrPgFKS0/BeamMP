## What this is

A **LAN-only fork of [BeamMP](https://github.com/BeamMP)** (multiplayer for
BeamNG.drive), stripped of the public backend/authentication so it runs entirely on a
local network with no internet dependency. It is tuned and tested across two machines:

- **LAN1** — Windows host (strong: i9-9900K). Runs the server. Best place for AI/weapon
  cars (the owner pays their AI + physics + send cost).
- **LAN2** — remote client (weaker; runs **CachyOS Linux + the LAVD `sched_ext`
  scheduler**). The machine the per-client performance toggles matter most on.

Three components, each built separately:

| Path | Language | Role |
|---|---|---|
| `BeamMP/` | Lua + AngularJS UI | The client mod (the BeamMP.zip the launcher installs into BeamNG) |
| `BeamMP-Launcher/` | C++ | Installs the mod + proxies the client↔server connection |
| `BeamMP-Server/` | C++ | The dedicated server / relay |

## Publishing a release

The BeamMP mod repo doubles as the fork's landing/distribution repo. On each release, after
rebuilding `BeamMP.zip` + the exes and assembling `dist/release-p13hNN/` → `dist/BeamMP-LAN-p13hNN.zip`
at the workspace root, MIRROR into the mod repo and commit on `lan`:

- `BeamMP/docs/lan/` ← RELEASE-NOTES.md, README-LAN.md, LAN-TUNING.md, CachyOS_Install_LAVD.md
  (the workspace-root copies stay the working canon; the repo copies are the published snapshot)
- `BeamMP/dist/BeamMP-LAN-p13hNN.zip` ← the release bundle, + update `BeamMP/dist/README.md`
  (sha256 table, current version line, tag name)
- `BeamMP/tools/` ← the workspace-root build/host scripts (build-*.bat, devenv.bat,
  build-linux-docker.sh + linux-build-inner.sh, package_mod.sh, apply-windows-tuning.ps1,
  host/) — re-mirror whenever a root script changes; `tools/README.md` documents the
  sibling-checkout layout they expect

Then tag ALL THREE repos `lan-release-p13hNN` and push `lan --tags` (RELEASE-NOTES' AGPL section
promises complete source at that tag). Each zip adds ~50 MB to the mod repo's history — if that
gets heavy, switch future zips to GitHub Releases and keep only dist/README.md + checksums.

## Staying synced with upstream

Each of the three repos has an `upstream` remote (BeamMP `development`, BeamMP-Launcher `master`,
BeamMP-Server `minor`) and the fork lives on the `lan` branch. To sync: `git fetch upstream` then
`git merge upstream/<branch>` on `lan` — review what each upstream commit does first (this fork
took upstream's batch mod loading as a straight win; the connection-limit env var as inert).
A server merge means rebuilding BOTH exes (the combined launcher embeds the server as a lib).

## Build & package

**C++ (Windows):** run `build-server.bat` / `build-launcher.bat`. Both use the
VS2022 MSVC toolchain, Ninja, and **static** vcpkg triplets (`x64-windows-static`).
The launcher points its toolchain at `BeamMP-Server/vcpkg`.

**C++ (Linux):** `build-linux-docker.sh` builds both binaries in a container into
**`bin-linux`** (not `bin`, to avoid clobbering the Windows CMake cache) and copies
them to `dist/linux`. The launcher is built classic-mode (vcpkg install run from a
neutral dir, `-DVCPKG_MANIFEST_MODE=OFF`).

**The mod zip (`BeamMP.zip`):** `package_mod.sh` documents the exact contents, but it
calls `zip`, which is **not available on this Windows box**. Build the zip with the
.NET method instead (this is the supported path here):

```powershell
# from repo root; backs up the old zip, then rebuilds from BeamMP/
$root='<repo>'; $mod="$root\BeamMP"; $out="$root\BeamMP.zip"
if (Test-Path $out) { Copy-Item $out "$root\dist\BeamMP_backup-$(Get-Date -Format yyyyMMdd-HHmmss).zip"; Remove-Item $out -Force }
Add-Type -AssemblyName System.IO.Compression.FileSystem
$dirs=@('icons','lua','mp_locales','scripts','settings','ui','vehicles')
$files=@('CONTRIBUTING.md','CODE_OF_CONDUCT.md','LICENSE','README.md','NOTICES.md')
$bs=[char]92; $fs=[char]47
$zip=[System.IO.Compression.ZipFile]::Open($out,'Create')
try {
  foreach($d in $dirs){ $b="$mod\$d"; if(Test-Path $b){ Get-ChildItem -LiteralPath $b -Recurse -File | %{ [System.IO.Compression.ZipFileExtensions]::CreateEntryFromFile($zip,$_.FullName,$_.FullName.Substring($mod.Length+1).Replace($bs,$fs),'Optimal')|Out-Null } } }
  foreach($f in $files){ $p="$mod\$f"; if(Test-Path $p){ [System.IO.Compression.ZipFileExtensions]::CreateEntryFromFile($zip,$p,$f,'Optimal')|Out-Null } }
} finally { $zip.Dispose() }
(Get-FileHash $out -Algorithm SHA256).Hash
```

> Note: `package_mod.sh` deliberately omits the cosmetic "Beamlings" avatars (a private
> upstream repo, not needed for LAN). The .NET packer above mirrors its file list.

## Deploy (where the artifacts go)

| Artifact | Destination |
|---|---|
| `BeamMP.zip` | `D:\BeamMP Launcher\` (next to the launcher exe) — on **every** machine |
| Server binary + config | `D:\BeamMP Server\` |
| Third-party mods | `D:\BeamNG_Mods\` (synced via the server); versioned copies in `D:\BeamNG_Mods\_mod_versions\` |

**Deploy changed mods cold:** stop the server while swapping any changed `.zip`, so
clients re-sync the new hash on connect. Swapping a mod mid-session leaves BeamNG with
the stale copy mounted (a real bug we hit). The new "Optimize map markers" toggle and
the options-menu changes are confirmed deployed when the new items appear under
**Options → Multiplayer → (advanced) → "LAN — position sync & performance"**.

## LAN feature toggles (intent + defaults)

All live in `BeamMP/lua/ge/extensions/MPConfig.lua` `defaultSettings` and appear as
checkboxes under **Options → Multiplayer** (with "show advanced options" on). The
position-sync/perf ones are grouped under a **"LAN — position sync & performance"**
header in `ui/modules/options/multiplayer.partial.html` (deleted in the 0.39 port -- see the
staleness note at the top of this file).

| Setting | Default | Intent |
|---|---|---|
| `physicsRateSend` | **on** | Emit own-car position from the VE physics step (at `physRateSendHz`) instead of once per render frame, so low-FPS machines still send fresh data. Send-side; no wire-format change. |
| `physRateSendHz` | **30** | Own-car position send rate (Hz). UI select **60 / 30 / 10**; the 100 Hz option was removed (it oversubscribed the ~150 pkt/s single-path relay → remote tracking degraded over a session). Lower is better — the predictor interpolates between updates. A saved value >60 is clamped + migrated to 30 in `positionGE.refreshFlags`. Host in-memory position buffers tightened 256→16 (p13h28). |
| `mailboxApplyPos` | **on** | Deliver incoming positions GE→VE via the engine mailbox (`be:sendToMailbox`) instead of a per-packet `queueLuaCommand`. ~25–40% cheaper apply. Falls back to the base64 `queueLuaCommand` path when off. |
| `optimizeMapMarkers` | **on** | Disable BeamNG's per-frame `gameplay_markerInteraction.onPreRender` (mission/POI marker raycasts — an FPS sink, useless for LAN) during a session; restored on leave. Ported from Olrosse/BeamMP `minimap_lag_workaround`. |
| `syncFullDeformation` | **off** | Broadcast full node/beam deformation (crash damage matches everywhere). Heavy CPU/bandwidth. |
| `enablePosSmoother` | **off** | Upstream smoother; leave off on LAN. |
| `profilePosSync` | **off** (DEBUG) | Log avg/max/rate of the position hot path to `beamng.log` every ~5 s (grep `posProf`). |
| `showSyncStats` | **off** (DEBUG) | On-screen overlay: synced vehicle count + net packet rates. |
| `autoSpawnMode` | `0` | Auto-spawn a car on join (0 off / 1 default car / 2 last used). |
| `aiChaseNearestPlayer` / `aiChaseIncludeSelf` | **off** | AI/weapon cars chase the nearest other player (lets one car chase everyone → fewer spawned cars). |

The matching GE flags are cached in `positionGE.lua` and pushed to every vehicle's VE
state via `refreshFlags()` (called on init and on every settings change), so the
position-sync toggles apply **live**, no rejoin — except `optimizeMapMarkers`, which is
applied at join (it swaps an engine hook in `multiplayer/multiplayer.lua`).

## Conventions (follow these)

- **Version + back up any mod you change.** Before editing a third-party mod, copy the
  original to `D:\BeamNG_Mods\_mod_versions\<name>_backup-<date>.zip` and write the new
  one as a versioned copy. For `BeamMP.zip`, the packer above auto-backs-up to `dist/`.
- **Guard every BeamNG engine call** you add (`if gameplay_markerInteraction then …`,
  `if veh and veh.setActive then …`). BeamNG's Lua/vehicle API churns between versions;
  a guarded call no-ops safely instead of breaking the whole mod. This fork tracks the
  `development` branch of the game.
- **Any per-vehicle VE flag pushed from GE must also be re-pushed in `positionGE.veReady()`.**
  A vehicle EDIT/config change reloads that vehicle's VE VM **in place** (same object id),
  silently resetting every VE-side flag to its default — and one-time setup gates on the GE
  object wrapper (e.g. `veh.mpVehicleType`) survive the reload, so they never re-fire. That
  exact hole froze ghosts permanently after their owner swapped cars (p13h50). `positionVE.onInit`
  announces every VM (re)load to `positionGE.veReady`, which re-pushes all flags; if you add a
  new pushed flag and skip veReady, it will silently die on the first vehicle edit.
- **The watchdog/overlay drift metric is dual-anchor** (p13h50): it compares the received COG
  against BOTH the refNode and the OOBB center and uses whichever is closer. Don't "simplify"
  it back to one anchor — OOBB-only lies for weapon vehicles whose node projectiles stretch the
  bounding box hundreds of meters (fake 100m+ drift, false heals); refNode-only lies for long
  vehicles by their COG↔refNode gap (the p13h27 bus false-snaps).
- **Don't change the server wire format** (the `Zp:` JSON position payload) without a
  both-ends + server plan and profiling proof — it's shared by every client and the
  relay. Local apply/processing changes (e.g. `mailboxApplyPos`) are safe because they
  leave the wire alone.
- **Relay throughput** is a known ceiling (single-threaded `UDPServerMain`, ~150–200 pkt/s
  aggregate; measured overloaded at 208 pkt/s / 8 vehicles). The safe O(1) client-lookup win
  is done (p13h31); the bigger moves (snapshot distributor, interest management, multi-threading)
  are scoped — all HIGH-risk — in **`RELAY-SCALING.md`**. Until then the lever is fewer live
  vehicles, not code.
- **Ship risky/unverifiable perf changes behind a default-off toggle**, keeping the
  original path as the fallback. The fork's pattern is to A/B every perf change in-game
  before flipping a default — and to *remove* a toggle that proves to be a footgun
  (e.g. `fastPredict`/`Low-GC predictor` was removed in p13h45: an audit found it
  correct but its GC win marginal under LuaJIT, so it only added a parallel code path).
- **`modVersion`** (`MPCoreNetwork.lua`) is **display-only** (shown in the CEF UI); it is
  **not** a handshake/compatibility gate here. Bumping it changes only the on-screen
  string.
- **Lua has no toolchain on this box** for parse-checking. Verify edits by careful review
  + matching existing precedent (e.g. `goto` targets, in-place `mathlib` methods exist:
  `LuaVec3:setAdd/setSub2/setScaled2/setLerp`, `LuaQuat:setMulInv2`).

## Profiling & testing

Enable `profilePosSync` on **both** machines (`settings.setValue("profilePosSync", true);
positionGE.onSettingsChanged()`), drive/crash for ~20 s, then read `posProf` lines from
`beamng.log` (`Select-String posProf` on Windows / `grep posProf` on Linux; the log is at
`%LOCALAPPDATA%\BeamNG\BeamNG.drive\current\beamng.log` or
`~/.local/share/BeamNG.drive/current/beamng.log`). Keys: `getVehicleRotation` = send,
`applyPos`/`setVehiclePosRot` = receive, `updateGFX.frames` = FPS, `updateGFX.stale` =
predictor starvation. See README-LAN.md for the full settings-for-the-test table.

**Log bundling.** `MPConfig.collectProfilingLogs()` zips `beamng.log` + rotations into the
`profLogFolder` subfolder of the user folder (auto-runs when `profilePosSync` is toggled off
if `autoCollectProfLogs`); also a "Collect logs (zip)" button in Options → Multiplayer →
advanced → DEBUG. Copy the zip off manually to compare machines. **Do NOT add a server-upload
feature over the event channel** — it was tried and removed: `MPGameNetwork.sendData` retries a
failed send indefinitely on the GE thread, so any multi-MB payload (even paced per-frame) hangs
the game (`STATUS_APPLICATION_HANG`). The `server-plugins/BeamMPLogReceiver/` plugin is the
now-unused receiver from that attempt (harmless if left deployed).
